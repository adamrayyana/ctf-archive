C++ Exception Handling Mechanism / C++异常处理机制介绍

C++ 里的 try-catch 本质上是"异常传播与捕获"机制：

Try-catch in C++ is essentially an "exception propagation and capture" mechanism:

当 throw 发生时，程序大致会做这么几件事：

When a throw occurs, the program roughly does the following:

  • 寻找合适的 catch / Search for a matching catch:

    抛出异常后，从当前函数开始寻找匹配的 catch。如果没有，则向上遍历调用栈（父函数、祖父函数……），直到找到能处理该类型的 catch。这就是 Stack Unwinding（栈回溯）。如果最后都找不到，用 std::terminate()，其默认行为是 abort。

    After throwing an exception, start from the current function looking for a matching catch. If none found, traverse upward through the call stack (parent function, grandparent function...) until finding a catch that can handle that type. This is Stack Unwinding. If ultimately none is found, call std::terminate(), whose default behavior is abort.

  • 转移控制到 catch handler / Transfer control to catch handler:

    一旦找到匹配的 handler，控制流跳转到对应的 catch 块。

    Once a matching handler is found, control flow jumps to the corresponding catch block.

  • 恢复执行 / Resume execution:

    异常处理完毕后，系统会尝试恢复执行，一般会继续执行 try-catch 块后面的代码。

    After exception handling is complete, the system attempts to resume execution, generally continuing with the code after the try-catch block.

Minimum Compilable Syntax / 最小可编译语法：

try {
    // 可能抛出异常的语句
    // Statements that might throw exceptions
    throw 表达式;
    // 表达式可以是任意类型 (int, std::string, ...)
}
catch (const 异常类型1& e1) {
    // Handle exception type 1
}

// g++-9 -Wall vuln.cpp -o pwn_input_no_catch
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

class foo {
public:
    char buf[0x10];
};

void input(foo *f) {
    read(0, f->buf, 0x100);  // Buffer overflow!
    throw "Exploited!";
}

void backdoor() {
    try {
        system("/bin/sh");
    } catch(const char* e) {
        printf("Caught: %s\n", e);
    }
}

int main() {
    foo f;
    try {
        input(&f);
    } catch(...) {
        puts("Exception caught in main");
    }
    return 0;
}

这时候，试运行程序，程序的走向根据输入的不同会有三种可能性：

At this point, when trial running the program, there are three possibilities for program flow depending on input:

  1. 程序正常运行并正常退出

    Program runs normally and exits normally

  2. 程序抛出异常，但是在input函数中就被捕获

  3. 程序抛出异常，但是在input函数中没有相对应的catch，那么程序流的走向：

    Program throws exception, but there's no corresponding catch in input function. Program flow:

throw in input() ↓ No catch in input() → Stack Unwinding begins ↓ Search parent (main) for matching catch ↓ Found catch(...) in main → Execute catch handler ↓ (__cxa_begin_catch → handler code → __cxa_end_catch) ↓ Continue after try-catch in main
🚨 KEY VULNERABILITY / 关键漏洞点

不难看出，当如果程序中途抛出了异常，那么接下来的代码一般是不会执行的（除非这个函数中有catch），而是直接去一层层 unwind，寻找匹配的 catch handler 。

It's not hard to see that if the program throws an exception midway, the following code generally won't be executed (unless there's a catch in that function). Instead, it directly unwinds layer by layer looking for a matching catch handler.

一般来说 canary 都是在函数即将返回的时候检测的，位于函数代码的最下面。那么，如果我们中间 throw 了异常，就不会往下执行剩余的代码，这其中就包含了 canary 的检测。即，我们无视 canary 返回到了某个 catch handler 分支。

Generally, the canary check happens when the function is about to return, located at the bottom of the function code. So if we throw an exception in the middle, the remaining code won't execute - this includes the canary check! That is, we bypass the canary and return to some catch handler branch.

The Crash Analysis / 死亡姿势分析

发现死亡姿势为：卡死在 cmp byte ptr [rax], 0x48

Found the "death posture": Stuck at cmp byte ptr [rax], 0x48

Original blog - Exception handling mechanism explanation / 原博客 - 异常处理机制解释

这句汇编：把 RAX 指向的那 1 字节内存内容与常量 0x48 做比较，根据比较结果设置标志位（ZF 等），后面的 je/jne 等条件跳转指令会用到这些标志位。

This assembly instruction: Compares the 1-byte memory content pointed to by RAX with the constant 0x48, sets flag bits (ZF, etc.) according to the result. Subsequent conditional jumps like je/jne will use these flags.

💡 KEY INSIGHT

合理猜测，程序是不是根据这个返回地址值确定上哪找 catch 块呢？因为如果我们不修改这个返回地址的值的话，它的值默认是 main 中 throw 的地址。

Reasonable guess: Does the program determine where to find the catch block based on this return address value? Because if we don't modify this return address, its default value is the address of the throw in main.
